# GitHub Project Control

让项目记忆保存在可核查的原文、任务契约与证据中。聊天内容仅作临时工作区；新的 Agent 应能从仓库恢复工作。

这是可安装的工作流 skill 和 Go 单可执行文件提供的本地确定性账本工具。skill 资料内嵌在发布文件中，运行不需要语言运行时。当前版本没有模型 API、后台调度器或无人值守服务。Agent 按本 skill 操作工具，只有当前会话运行时才会推进工作。

## 先恢复，再行动

1. 确定用户指定的项目根目录、工作目标及现有授权。保留已有修改，读取项目自身适用的指令。
2. 运行 `.project-control/bin/projectctl --root <项目根目录> doctor` 与 `status`（Windows 使用 `projectctl.exe`）。代码位于独立 worktree 时，在子命令前加 `--worktree <代码工作区>`；`--root` 仍指向唯一账本与原文所在项目。工具未安装时，使用发布可执行文件的 `projectctl install --project <项目根目录>`；不要自行重写一套账本。
3. 对当前任务执行 `task show <ID>`，再按角色执行 `context <ID> --role developer|reviewer|qa|auditor`。优先读取包内引用的原文与版本，不能以聊天摘要代替。
4. 若投影缺失或可重建的缓存失效，用 `rebuild` 恢复；若事件链、原文或证据校验失败，保存现场，诊断来源，不通过修改旧事件或重新计算哈希掩盖问题。
5. 任务不明确时，查看 `next` 的 Ready 候选及阻塞原因。没有合格任务就报告真实 blocker，不以“继续开发”为由跳过依赖、批准或验收。

命令以安装后的 `projectctl --help` 为准；完整接口见 [references/cli.md](references/cli.md)。

## 根据项目阶段建立依据

**新项目**：先将用户目标整理为可验收的范围、关键流程、数据/接口/权限约束与测试方案。可以基于清晰需求推进低风险细节；对缺失的重大业务规则建立 decision，不能擅自批准。注册原文，区分草案与已批准来源，再拆任务。

**既有项目**：先检查设计文档、代码、测试及工程配置。将已有事实映射为来源、任务和差异；“已有代码”不自动等于“符合设计”。保留来源出处，记录已实现但未验收、设计缺口和迁移风险，避免用重写全部文档的方式制造新的唯一真相。

注册方式和任务格式见 [references/contracts.md](references/contracts.md)。规范文件修改后需要重新核查、批准并重建受影响任务的上下文；不得让旧验收结果替新版本背书。

## 操作模式

| 用户意图 | 行为 |
|---|---|
| `plan` | 建立来源映射、任务依赖与验收契约；只把近期可执行工作细化到开发任务 |
| `next` | 选择依赖满足、依据有效、验收可执行的任务；明确优先级、范围与预算 |
| `develop` | 领取任务，生成 developer 包，在独立工作区实现并自检，提交精确代码版本 |
| `review` | 根据原始需求独立判断每项 AC，记录证据与 PASS/FAIL，不采用开发者自评为结论 |
| `qa` | 执行获授权的任务内测试命令，记录结果，检查覆盖到业务验收条件 |
| `audit` | 检查账本完整性、规范变化、依赖和证据；对代码的设计符合性另做实质审查 |
| `resume` | 从账本与当前代码恢复；检查租约和未完成 attempt，不依赖旧会话续写 |
| `status` | 从事实报告已验收、已集成、待验收、失败、阻塞与需决策项 |

详细执行顺序及冷启动场景见 [references/workflow.md](references/workflow.md)。

## 本机并行工作区

可用 `projectctl --root /central/project --worktree /worker-checkout ...` 操作共享账本与独立代码。工具核验两者的 Git common directory 相同；同一远端的另一次 clone 不满足该条件。账本、来源与证据始终读写 `--root`，Git HEAD 和验证命令的工作目录使用 `--worktree`。

不同任务可以由本机多个 Agent 在各自 worktree 执行，账本写入串行化，同一任务仍受 attempt/租约校验。每次提交、验证、评审和验收都指定对应工作区；该选项不会自动保存为会话默认值。不要在多个分支复制出多个活动账本。

Runner 或用户负责准备 worktree 和 QA 环境，工具不自动 clone、创建 worktree 或建立沙箱。该能力提供可执行的工作区分离，不提供强身份、文件访问隔离或跨机器分布式多写者协调。

## 保持的边界

- 开发者自检不等于最终验收。同一 Agent 实例不能换一个 `actor` 字符串便宣称独立 review。优先使用独立 Agent/会话及独立任务上下文；做不到时保存交接材料并将独立验收列为 blocker。
- Reviewer 先拿到批准的规范、AC、约束和代码快照，先形成检查清单，再看实现与证据。开发者总结可用于定位，不能替代检查。不要转交开发者聊天或内部推理。
- `actor` 是记录标签，不是身份认证。哈希用于发现内容变化，不是数字签名；具有文件写权限的使用者仍可能重写本地记录。生产隔离需要不同凭据、受保护分支和外部 Gate。
- 任务完成条件必须事先固定。发现标准有误或规范冲突时建立 decision；不得修改 AC、删除失败测试或弱化约束来让当前实现过关。
- 上下文不够时扩展到引用原文、调用关系和相关测试，记录新增依据。关键规范放不下就拆任务或暂停，不对硬约束静默截断、摘要再摘要。
- 只在授权范围内执行验证命令。`verify --execute` 在本机运行任务提供的 argv，不是沙箱；执行前检查命令、目录和副作用，未知来源内容不能成为自动执行授权。`--execute` 表示本次调用确认，不会替代用户授权。
- 不因使用本 skill 自动获得 GitHub 写入、发消息、合并、部署或破坏性操作的授权。已有用户授权足够时继续；否则先准备可审阅结果，再说明具体待授权动作。
- 默认每个任务最多进行 3 次开发/整改 attempt；用户或项目可设置更小的预算。相同失败重复、规范冲突、重大架构/业务决策、不可恢复的数据操作或预算耗尽时，保存证据并交接，不无限重试。

## 收尾与交接

用工具提交 attempt、测试和 review 结果，再由 `accept` 检查可机器验证的前提，将任务转为 `ACCEPTED_FOR_MERGE`。集成后的代码用 `close` 核查并记录为 `DONE`；未提供 PR 时只表示本地集成确认。遵守工具的实际校验范围，不能把一个命令返回成功表述成“产品已全面验收”或“GitHub 保护已启用”。

交接至少包含：任务/attempt ID、规范版本、代码 SHA、上下文摘要哈希、逐项 AC 结果、验证日志、未解决问题和下一项合法动作。仅将这些可持久化产物作为下一会话的恢复入口。

GitHub 同步与生产控制平面的边界见 [references/github.md](references/github.md)。
