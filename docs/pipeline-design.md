# Projectctl 全新设计：有边界的自动开发流水线

状态：全新目标设计，尚未发布为可运行产品，也尚未形成远端批准基线。本文是新架构的唯一规范；其他设计入口只链接本文。现有代码、命令、安装方式、数据格式和兼容需求均不构成约束，不规划旧账本迁移层。

## 1. 产品定义与边界

用户输入产品文档、开发文档和工程约束，系统在项目启动期完成开发方案与任务规划；冻结后，由独立 Agent 完成开发、验收、有限整改、合并和分支清理，最后对交付目标整体验收。

产品是**自动流水线控制器**，不是要求用户手动调度的命令集合，也不是一个持续产生新任务的聊天 Agent。

首版边界：一个 GitHub 仓库、一个交付周期、一个受控 Controller、可隔离的开发与验收运行环境。支持已有仓库，但已有代码只是设计输入，不要求兼容 Projectctl 自身旧架构。跨仓库、分布式多主调度、多宿主自由抢任务、大型管理看板不进入首版。

默认交付终点为“指定代码版本完成集成验收且清理完成”。部署和目标环境验证必须在启动时明确纳入范围并授权；系统不因为代码合并成功便宣称已经上线。

### 不可破坏的原则

- GitHub 是唯一持久执行账本：项目决定、任务、证据、缺陷及交付结论都在 GitHub；本地不保存可独立推进的状态。
- 先设计，后规划，再执行。重大业务与技术决策不得推迟到开发 Agent 临场决定。
- 一个执行 Issue 对应一个固定开发分支；一个 PR 只交付一个执行 Issue。验收发生在实现 PR 上，不另开“验收 PR”。
- 开发与最终验收为不同 Agent 实例，且具有真实的执行、工作区和发布权限隔离。
- PR 合并后关闭对应执行 Issue，并清理远程和本地开发分支；优先使用 GitHub 原生自动关闭与自动删除能力，控制器对账并补齐例外。
- 合并是事实，不等于验收、上线或清理完成；这些结果分别核查。
- 执行有固定范围、预算和停止条件；Bug 修复不能成为无限扩张的通道。

## 2. 从文档到交付的六个阶段

| 阶段 | 产物 | 离开本阶段的门槛 |
|---|---|---|
| 启动 | 项目控制 Issue、原始输入、授权政策 | 仓库/目标/角色/预算/交付终点明确；输入允许存入该 GitHub 仓库 |
| 设计 | 完整开发方案与独立设计审查 | 重要决策无悬而未决；设计审批绑定精确版本 |
| 规划 | Milestones、全部执行 Issues、依赖图、覆盖检查 | 覆盖完整、依赖无环、切片可验收、计划批准冻结 |
| 执行 | 每个 Issue 的分支、PR、验证及 Review | 独立验收和合并门禁通过，合并及两端分支清理 |
| 交付 | 固定源码/产物版本上的集成与必要环境验证 | 满足交付条件，无阻断缺陷，收尾无遗漏 |
| 结束 | GitHub 中的交付结论或明确停止原因 | 不继续自动发明需求；后续工作需新周期或明确变更 |

```text
输入文档 → 完整设计 → 独立设计审查/冻结 → 全量切片/计划冻结
                                               ↓
                                      选择依赖已满足的 Issue
                                               ↓
                                      Developer → 实现 PR
                                               ↓
                                      独立验收 → 合并门禁
                                         ↑失败       ↓通过
                                      有限整改    合并 → 双端清理
                                                     ↓
                                        固定交付候选 → 整体验收 → 结束

设计缺口/范围变化 → 阻塞受影响范围 → 变更审查 → 新基线/新计划修订
```

### 2.1 设计必须回答的问题

设计 Agent 根据原文形成：需求编号和边界、关键业务流程与异常路径、模块职责、接口、数据模型、权限、外部依赖、技术选型、运行环境、测试策略、集成顺序、交付/回滚条件，以及已识别风险。

“设计完整”不是提前写出所有函数，而是足以让不同 Agent 独立实现并得出一致的接口和验收预期。函数内部结构、局部命名等不影响契约的细节由 Developer 决定。

独立设计审查检查原文覆盖、一致性、可实现性和可验证性；模型不能把自己补写的业务规则当作用户已批准。重要不确定性可先做有限技术验证，但验证产物不直接作为未经审查的正式实现合并。

设计准备自身使用一个非产品实现的设计 Issue 和文档 PR，仍遵循 Issue/分支关联。它是启动期的明确例外，只能修改输入、方案和启动资料；不借此绕过开发冻结门。冻结引用已合入 GitHub 的设计提交，原始外部文档须在授权下固化进仓库，不依赖随时变化的外部链接。

### 2.2 规划一次覆盖整个交付范围

Planner 在冻结设计上生成全部 Milestones 和执行 Issues，而不是每完成一项再临时发明下一项。每个切片应能基于已合并的依赖独立开发、验收和合并；不以“文件数量”或“前端/后端”替代交付目标。

Issue 必须包含：覆盖的需求编号、目标和非目标、具体 AC、验证办法与环境、预期影响面和风险。依赖使用原生 Issue blocking 关系，Milestone 使用原生归属。

计划检查必须覆盖：每条需求有负责切片、AC 可验证、依赖无环、没有重复交付、外部条件可获得、关键集成路径有专门验收。需求覆盖关系从契约推导，不另写一份可编辑映射。

冻结记录保留可枚举的完整成员清单：每个 Issue 的稳定 ID、契约记录引用及摘要，连同原生依赖与 Milestone 关系的总摘要。这样任务被移走、关闭或删除时不会从冻结范围中“消失”。该清单是批准事实，不保存任务状态副本。

设计批准与计划批准是两个门槛。可按项目初始授权把满足指定条件的计划批准委托给独立审查者；涉及业务规则或扩大范围的决定仍由授权所有者处理，不要求用户逐个批准执行 Issue。

## 3. 对象模型与唯一事实归属

一个项目控制 Issue 管理一次交付周期。Milestone 聚合阶段目标；执行 Issue 承载可交付工作；Bug、变更和交付记录按下表归属。

| 事实 | 唯一权威位置 | 禁止作为第二权威的位置 |
|---|---|---|
| 产品输入、设计、接口与策略内容 | GitHub 仓库中的精确提交/路径 | 本地方案副本、聊天摘要 |
| 当前批准的基线、计划成员、预算、授权及修订 | 项目控制 Issue 中的结构化决定记录 | README 进度表、本地数据库 |
| 切片契约、AC、需求覆盖和验证办法 | 对应 Issue 的版本化 contract comment | PR 正文、控制 Issue 中重复的 AC |
| 依赖与 Milestone 归属 | GitHub 原生关系 | 契约中再写 dependencies/milestone 字段 |
| PR 对应的执行 Issue | PR 与 Issue 的原生关闭关联，由 PR 正文 `Closes #N` 建立 | 自定义 delivery 字段、按标题猜测、同时关闭多个 Issue |
| 实现代码、head/base、合并事实 | GitHub Git 对象与 PR 原生元数据 | 自报状态、Issue closed |
| 验证与逐项验收 | PR 上的 evidence comment 与原生 Review | 本地测试账本、开发者自评 |
| 合并准入检查 | 可信 Gate 发布的原生 Check | 普通用户创建的同名状态 |
| Bug 症状与影响 | 唯一 PR finding 或唯一 Bug Issue | 重复 Bug、另一份本地缺陷表 |
| Bug 分诊、批准延期和目标环境结论 | 主记录上的授权结构化记录 | label 名称、自由文本“已修复” |
| Agent 分配、尝试及预算消耗 | 所属 Issue 的 run record | 本地 attempt 文件、会话记忆 |
| 交付候选与总体验收 | 项目控制 Issue 的 delivery record | Milestone 完成百分比 |
| 分支和工作区是否仍存在 | 远程 Git ref、受管宿主实际 Git/workspace 状态 | “清理成功”缓存标记 |

Issue 正文提供说明和记录入口，不重复保存执行契约。contract comment 是 Issue 内的唯一契约正文；批准后的记录只追加新版本，不原地覆写。未批准的新 comment 不改变执行依据。该选择使用户可以读懂 Issue，也避免可变正文和冻结快照同时成为权威。

GitHub 中的记录并非不可篡改档案。关键引用同时包含稳定对象 ID、内容摘要及原生作者；被编辑、删除、冲突或不可访问时必须阻塞，不能使用本地备份静默替代。管理员权限本身是信任边界，不声称可抵抗仓库所有者恶意篡改。

label、assignee、看板、状态页面和终端输出只用于导航与即时展示，不用来证明领取、验收或完成。不持久化第二份状态投影，也不做本地与 GitHub 双向同步。

### 3.1 最小记录协议

所有结构化记录含 schema、kind、project/subject ID、稳定 operation_id 和精确引用。自由文本、提示词中的 actor 或自称“已批准”不产生权限。

- **基线记录**：输入与设计提交、策略版本、设计审查引用、授权审批引用。
- **计划记录**：父修订、基线引用、Issue/契约成员清单、关系摘要、预算与完成条件；不复制契约或进度。
- **契约记录**：目标、范围/非目标、需求编号、AC、check 定义/环境、影响面；由计划显式选择其版本。
- **运行记录**：角色、Agent 实例、宿主、任务输入摘要、分配代次、尝试额度、时间/费用上限与最终结果；结果指向 GitHub 证据。
- **证据记录**：PR、head SHA、验证时 base SHA、基线/契约/策略摘要、可信执行实例、命令/环境、退出结果、日志摘要。
- **验收记录**：逐项 AC 结论、证据引用、未解决 finding、同一版本绑定及独立验收身份。
- **交付记录**：计划修订、源码 SHA、需要时的构建产物摘要、环境/部署引用、集成证据、Bug gate 和收尾结论。

设计和计划的授权决定必须能解析为策略允许的真实 GitHub 身份；审批引用准确候选摘要。“LGTM”或一次笼统聊天不能被转换成无限未来授权。

## 4. 系统组件与权限边界

采用一个确定性控制核心，外接 Agent Runtime 和 GitHub，不让语言模型决定账本是否已成功变更。

| 组件 | 责任 |
|---|---|
| GitHub Gateway | 完整分页读取对象、核对身份/关联/摘要、提交受控写操作；不维护另一份数据库 |
| Reconciler | 从实时事实推导阶段与合法下一步；事件只是唤醒提示 |
| Policy / Gate Engine | 设计/计划冻结、授权、预算、证据与合并门禁；输出可解释阻断原因 |
| Scheduler | 基于 DAG、风险/影响面、可用额度和隔离资源分配任务；不创造需求 |
| Agent Runtime | 启动、查询、取消独立 Agent；限制时间/费用/工具与上下文；返回真实运行标识 |
| Workspace / Sandbox Manager | 创建隔离工作区、准备精确版本和环境、保存必要产物、停止进程与安全回收 |
| Trusted Publisher | 核查有效分配及输出后，以受控身份发布分支、PR、证据、Review 和 Check |
| Merge / Delivery Executor | 执行经 Gate 准入的合并、清理和已授权部署；不能自行降低标准 |

所有组件可以先在一个受管服务中实现，不要求微服务。CLI 与 skill 是调用和解释接口，不是编排引擎，也不以活跃聊天会话替代后台服务。

Agent Runtime 的最小接口是 start(input_ref, assignment)、inspect(run_id)、cancel(run_id)。具体供应商适配器必须证明独立实例、隔离运行、终止能力和预算约束；首版只实现一个合格适配器，不先做多平台兼容层。

### 4.1 角色分工

Design Agent 产出方案；独立 Design Reviewer 审方案；Planner 切片；Developer 写实现；独立 Acceptance Agent 同时负责实际验证和逐项审查；Bug Triager 负责去重和归类。必要时验收可拆 QA/Reviewer，但不强迫每次运行更多 Agent。

Acceptance Agent 从原始依据、Issue 契约和精确代码开始，不继承 Developer 聊天；开发总结只作导航。验收者修改产品代码后，不再有资格独立验收自己的修改，必须换人。

至少隔离开发发布身份、验收发布身份和控制/Gate/合并身份。发布器验证真实分配与身份，不接收模型自填 actor。GitHub 身份不同只是必要可审计条件，不能代替不同 Agent 实例。

待测代码和 Agent 沙箱不得持有 Review、Gate、合并或审批 token。验证进程与证据发布器分离；发布器不执行候选代码。GitHub 仓库级权限不能直接表达“只能改这一条 Issue”，需由发布器限制具体资源与动作。CI 工作流、门禁策略和运行镜像从可信批准版本加载，不能让当前 PR 修改后立即影响自身 Gate。

本地仅有连接配置、凭据句柄、可丢弃缓存及受管工作区。业务授权、预算和当前基线不放在本地配置。凭据由宿主秘密管理提供，不写入 Issue、日志或工作区。

## 5. 执行协议、收敛与恢复

### 5.1 固定分支与 PR

每个需要代码变更的执行 Issue 使用 `codex/issue-N`。从已满足依赖的目标分支创建，在自己隔离的工作区开发；不依赖另一个未合并 Issue 的分支。

同一 Issue 的开发和整改保留一个活动实现 PR。PR 关闭但未合并时优先恢复原 PR；确实无法恢复时，可由控制器记录 supersedes 后替换，但旧 Review/finding/预算不被洗掉，且不得并行存在两个交付候选。一个 Issue 最多产生一次被接受的实现合并；合并后不复活该分支。

首版所有实现 PR 以仓库默认分支为目标，正文只包含一个执行 Issue 的关闭指令 `Closes #N`；检查原生关联，禁止提交消息或正文附带其他意外关闭指令。合并后由 GitHub 自动关闭执行 Issue，Controller 必须确认其实际状态。GitHub 原生关联就是权威，不另设自定义 delivery 关联字段。

独立 Bug 主记录与代码修复执行 Issue 分开：修复 PR 关闭本次执行 Issue；Bug 通过普通引用关联，不放入自动关闭关联，按自身解决条件关闭。这样每次修复合并都关闭对应工作项，尚待部署复验的问题仍有准确主记录。设计/其他任务引用也只作背景，不共同关闭。

项目控制、纯缺陷报告、变更申请及纯验收记录不为凑形式创建空分支或空 PR；一 Issue 一分支约束针对需要修改仓库的执行切片。

### 5.2 调度与尝试预算

只有有效计划成员、依赖已有有效集成事实、无阻塞决定、资源和预算充足的 Issue 才可领取。优先级在冻结政策内决定；共享接口或高冲突影响面的切片串行，独立切片可并行开发。首版合并串行。

初始默认：同一切片最多 3 次实现/验收轮次，设计审查与规划也各有有限轮次；总运行时间、费用、缺陷修复及变更次数上限由启动政策明确。缺少必要上限不能启动无人值守模式。

每次运行在 GitHub 先登记分配和最大额度再启动；重启后未确认的运行继续占用预留额度，不能把费用当零。拆分、替换 PR、追加修复 Issue 不重置原问题的累计预算。

相同失败重复且无新依据、设计冲突、预算耗尽、缺失身份/环境分别形成明确的受阻原因。可重试基础设施故障必须区分产品失败；测试 flaky 不得靠反复跑到绿来通过，需在授权次数内完成诊断或阻塞。

### 5.3 对账循环而非本地状态机

```text
读取 GitHub 完整事实 → 校验版本/权限/预算 → 推导一个合法动作
        ↑                                      ↓
重新读取实际结果 ← 受控执行并发布必要记录 ← 登记动作意图
```

初版一个项目只有一个 Controller，由受管宿主的进程互斥和唯一凭据发布通道保证。运行归属是部署约束，不靠 Issue comment 模拟分布式锁。切换宿主前停止并隔离旧发布通道，再授权新宿主；不支持两个宿主自由抢占。

分配携带递增代次。沙箱只有本地写权限，所有远端写通过可信发布器；代次被撤销的旧 Worker 即使继续运行，也不能推送或提交有效验收。时间到期本身不是隔离，必须确认取消或执行围栏后才重新分配。

操作使用稳定 operation_id，网络超时后先查实际对象再决定是否重试。创建对象不假定 GitHub 提供跨对象事务或 exactly-once；无法确定是否创建成功时停止该步骤对账，发现重复对象时隔离候选并明确处置，不能随机选一个通过。

冷启动读取批准记录、冻结成员、运行额度、Issue/PR/Review/check/ref 和宿主进程现状。已经合并只做核查收尾，不重做开发；有未发布代码则保留工作区并尝试恢复。丢失的未推送工作可重做，但不能声称它已交付。断网时停止新的远端动作，不以本地镜像推进完成状态。

## 6. 验收、合并与分支收尾

### 6.1 每个 PR 的独立验收

验收者先根据冻结依据制定检查，再读取实现。必须逐项核对 AC，执行约定自动检查及必要的人工式探索，关注失败路径和范围外副作用。

验证结果绑定 `PR + head SHA + 验证 base SHA + design/contract/policy digest + run ID`。新 head、新契约或受影响的新设计使旧验收无效。相同版本的最新有效失败不能被更早 PASS 覆盖；撤销或缺失证据阻塞。

日志应脱敏。必要结论、可复现步骤和绑定信息写入 GitHub；大型日志可引用 GitHub 托管产物，记录摘要及保留期限。不可访问或过期且影响验收的证据必须重做，不以本地日志作为替代账本。

### 6.2 合并前最后一道门

自动合并需要同时满足：当前批准计划仍有效；当前候选与契约准确关联；独立验收通过；必需 CI 和整合测试通过；无阻断本候选的未解决 finding/其他 Bug；预算、授权和目标分支规则仍有效。修复 PR 正在处理的主 Bug 不要求先 resolved，否则会形成循环；它必须通过本次修复 AC 和独立回归，主 Bug 仍按第 7.5 节阻断最终交付。

首版采用串行合并、分支必须基于最新目标分支、可信 Gate check 和禁止绕过的分支保护。base 前进时更新当前分支并重新验证、审查新 head；不得把仅检查 head 的 API 参数当作 base 的并发锁。先验证仓库套餐、规则权限和保护能力，无法满足便拒绝开启自动合并，不降级为无保护合并。

合并请求使用刚验证的 head 条件；返回后读取真实 merge commit 和代码树，验证其与受验候选一致。head/base 变化、冲突、Check 失效或外部越权合并均进入重验/异常处置。未经有效 Gate 的外部合并记录为异常，阻塞受影响交付，不能追认旧 PASS。

未来可支持原生 merge queue 的合成候选检查，但它不是首版默认依赖，也不能绕过本产品的契约/身份验证。

### 6.3 原生收尾、Issue 关闭与本地清理

初始化预检读取仓库原生设置，优先启用 `Automatically delete head branches` 和 `Auto-close issues with merged linked pull requests`。前者是仓库级设置，不只影响 Projectctl 分支；修改须取得相应范围授权，不能在普通 run 中擅自修改。后者虽默认开启，也必须实查，不能只凭默认值假设。无法通过 API 读取某项设置时明确 unknown，要求有权限者确认，并在每次合并后核查实际效果。

合并前停止 Developer 的远端发布资格、封存精确候选，确保受管分支不再接收新提交；必要资料先保存。原生自动删远程分支不检查本地工作区，不能代替此步骤，也不能证明本地分支已删除。

合并后分别读取三个事实：

1. PR 已实际合并且执行 Issue 已关闭。优先等待并核查原生关闭；若设置关闭、关联失效或原生动作未完成，先核对正确 Issue 和有效合并，在授权内幂等补关并保留原 PR 引用。误合并或证据失效时记录异常，不把 GitHub 的自动关闭当作验收成功。
2. GitHub 上精确 head ref 已不存在。原生自动删除成功后不再重复执行远程 delete；保护规则或仓库规则可能阻止删除。仍存在时先判断原因，仅在权限与规则允许且 ref 仍等于已合并 head 时做条件删除；不能绕过规则强删。
3. 受管宿主上的本地开发分支已删除。停止进程、保存资料、解除工作区占用，再按预期旧值删除本地 ref；`fetch --prune` 只清理远程跟踪引用，不能当作删除本地开发分支。工作区另行安全归档。

GitHub 原生自动删除与本地清理不是事务。原生行为不能被表述成提供了应用层逐 ref 条件删除保证；系统通过合并前撤销写资格防止受管 Worker 迟到提交。需要保留或允许其他人继续写的分支不能用作一次性交付分支，必须在启动政策与仓库权限中解决。

补偿删除需核对仓库、完整 ref 和预期已合并 head；含后来提交、仍被占用或宿主无法确认时保留并报告。清理可幂等重试，某端已不存在视为该端无待做动作。不通过删目录强行解除占用。

`Integrated` 是有效验收后的合并事实；`IssueClosurePending` 和 `CleanupPending` 是独立收尾事项。依赖可基于有效集成继续，但执行 Issue 未关闭或清理仍有缺口时，流水线不能宣布完整结束。用户自行复制、系统未管理的机器不在“本地分支全部已删除”的证明范围内。

## 7. Bug 是质量闭环，不是新增需求入口

### 7.1 先确认记录归属

| 发现情况 | 唯一主记录 | 修复载体 |
|---|---|---|
| 当前未合并 PR 引入，属于当前承诺 AC | 原 PR Review finding | 原 Issue、原分支、原 PR 整改 |
| 已集成版本中的独立缺陷、合并后回归 | Bug Issue | 关联的修复执行 Issue，独立新分支/PR |
| 已存在相同问题 | 引用原 finding/Bug | 不重复建修复任务 |
| 只是新增能力或改变预期 | Change Issue | 先审设计/范围，不伪装 Bug |
| 环境/测试基础设施故障 | 所属 run 的失败证据 | 诊断；确认是产品缺陷后再分诊 |

未合并候选中的问题不能仅因影响广就移到另一个分支，让原 PR 带病合入。独立修复必须能从已集成基线启动。finding 升级成 Bug 时保留原 finding 和证据，追加 promoted_to 记录；后续处置在唯一 Bug 中继续，不覆盖或复制历史证据。原验收失败仍然成立，不能因“已建 Issue”变绿。

新的报告在项目控制 Issue 追加 discovery 引用（稳定对象 ID、摘要和发现版本），不复制症状或当前状态；它独立于计划成员，未入队的缺陷也能被恢复扫描，删除主报告会被发现为依据缺失。受控发布器登记后才确认报告已接收；外部报告由事件唤醒加完整扫描登记。尚未被系统观察且被外部删除的报告无法恢复，不能承诺可审计这类不可见事件。

### 7.2 报告、分诊与状态

报告包含：期望行为及基线/AC 引用、实际结果、最小复现、精确受影响源码/产物/环境、脱敏证据、影响范围、发现来源与疑似引入 PR。尚不清楚的项显式 unknown，不捏造复现成功。

独立分诊先去重，再判断实现缺陷/环境问题/需求变化，确定严重程度、优先级、阻塞对象和修复验收条件。严重程度与调度优先级分离：

- S0：数据丢失、严重安全问题或系统整体不可用；立即隔离，按已授权应急策略止损。
- S1：核心流程不可用且无可接受替代；阻塞受影响交付。
- S2：局部功能错误或存在替代路径；按影响调度，若违反承诺 AC 仍阻塞完成。
- S3：低影响体验或文案问题；按范围与预算处理，不自动加入当前承诺。

分诊处置为 confirmed、needs-info、cannot-reproduce、duplicate、not-a-bug/scope-change 或 deferred/wont-fix。当前权威来自最新有效、授权且明确 supersedes 的 triage 记录；labels 只帮助检索。未知而可能严重的问题保持阻塞，不能自动判定无问题。

状态从事实派生：Reported → Triaged → Repairing → VerifiedForMerge → FixedInCode → ResolvedInTarget；另有 NeedsInfo/Disposed。原 PR finding 在原 PR 中完成有限整改；独立 Bug 才拥有这条完整修复生命周期。

### 7.3 修复与回归

修复目标是恢复原有契约。独立验收至少包含旧版本失败/新版本通过的复现证据，以及相邻关键路径回归。无法确定性复现的间歇性缺陷，需要明确概率性验证计划和授权风险结论，不能编造稳定红绿测试。

已承诺范围的缺陷修复可在预留缺陷预算内，通过显式计划修订加入新执行 Issue；不必重做整个产品设计，但不得静默追加成员。改变行为预期、接口或 AC 必须走第 8 节的设计变更。

所有失败证据保留。新 PR、重新分诊或追加任务不清空主问题的尝试/成本，Developer 不能自行降低严重程度或删失败测试来通过 Gate。

### 7.4 合并不是 Bug 关闭条件

每个修复执行 Issue 都在其 PR 合并后关闭。Bug 主记录不是这个执行 Issue：若解决条件只要求代码级修复，独立回归及合并核查后关闭主 Bug；若缺陷发生在部署环境，必须验证指定构建已经部署到目标环境，并在那里复验后才关闭主 Bug、标记 resolved。尚未部署时保持等待，不把等待重复计算为实现失败。

首次修复已合并但目标环境证明仍未解决：保持同一个主 Bug，创建关联的后续修复 Issue；后者只保存修复契约并引用主 Bug，不复制症状/严重程度。后续修复各有新分支/PR，继承主问题预算，不复活已经合并的分支。

确已验证解决后，在后来版本重新引入，才创建新的 regression Bug 并关联原问题与版本。GitHub Issue 被提前关闭、修改 label、移出 Milestone，都不能消除冻结交付中的未满足条件。

涉及敏感漏洞时，先走项目已授权的 GitHub 私密安全报告渠道；报告、补丁提交、远程分支、PR、CI 日志和构建产物均受披露约束，公开协作最多保留已批准的非敏感阻断引用。无已授权私密修复及发布路径时，整个敏感修复发布进入 Blocked，不得自动推送普通公开 `codex/issue-N` 分支，不建立另一套私有本地 Bug 账本。

### 7.5 交付缺陷门

Gate 同时核查冻结成员、受控修订、相关 finding/Bug 与新分诊的关联阻断项，不只查询“当前 Milestone 下仍 open 的 bug”。

修复准入和最终交付是两道不同门。主 Bug 通过修复引用关联执行 Issue，不把“主 Bug 已解决”设成修复任务的启动/合并依赖；修复候选满足修复 AC、独立回归及其他阻断项要求后可以合并。为完成目标环境复验，可按已批准的修复/应急部署政策部署候选；这不是正式交付通过，也不是提前关闭 Bug。复验成功后再解除主 Bug 对交付的阻断。

S0/S1、任何未满足的承诺 AC 及未决高风险问题阻断相应交付。批准延期或风险豁免可允许特定发布，但不会把失败 AC 改成通过；若要缩减交付承诺，必须批准新计划，保留原承诺的历史。缺失或被删除的缺陷依据一律不可视为 resolved。

## 8. 受控变更：重新设计必须显式发生

发现设计缺口时创建 Change Issue，写明原依据、原因、影响需求/接口/Issues、预算影响和建议。Controller 暂停受影响任务；只有影响分析证明独立的其他任务才可继续。

任何活动计划修订（包括缺陷预算内的修复入队）都必须经过发布屏障：停止受影响派发，撤销相关分配，取消尚未发出的合并动作；对已经发出的合并先对账完成，撤销旧 Gate 资格，再启用新修订并重验。计划批准与合并发布在同一个受控通道串行处理，不能让 head 未变的旧绿色 Check 覆盖已经变化的规范。只有 Controller 可以激活修订；直接编辑 GitHub 记录视为漂移，不算发布新版本。

设计 Agent 更新方案，独立审查后由授权人批准；建立新设计基线及计划修订，新增/替换的契约在所属 Issue 中生效。旧证据不会自动沿用：按影响面使相关 PR、集成和目标环境验证失效。

冻结成员不能被删除以美化完成率；取消/替换必须记录明确处置，并由新计划覆盖原需求或批准其移出。每次变更计入次数和总预算，不允许无限“重新规划”刷新起点。

未批准的新想法留待后续交付周期，不阻塞已经有完整定义且独立的当前切片，也不由系统自动实施。

## 9. 交付终点和状态展示

Milestone 不是 Issue 关闭计数。系统在冻结源码版本上执行跨模块、端到端和约定非功能验收；纯验证不用制造空 PR。

一个 delivery record 指定本次源码 SHA、构建摘要（如适用）、计划修订、验收环境和证据。代码或构建变化产生新的候选，不能把前一个版本的绿色报告套用到新产物。部署仅在交付契约明确要求且已有授权时执行；生产风险需符合预设批准与回滚政策。

`status` 即时展示：当前阶段、冻结范围满足情况、运行/等待事项、阻断原因、剩余额度、Bug 和清理缺口，以及下一合法动作。每项都链接 GitHub 原始事实，不输出另一份需要人工维护的任务表。

流水线只在以下情况下停止：

- Completed：冻结范围及必要环境验收全部满足，Bug gate 通过，受管分支收尾完成。
- Blocked：需要业务决定、身份/环境修复、人工保全或不确定远端结果的对账。
- BudgetExceeded / Failed：授权额度耗尽或不可恢复失败，保留证据和未完成范围。
- Paused / Cancelled：授权人要求停止，撤销分配并处理在途操作；不伪称已完成。

## 10. 产品接口与实现切片

下面是目标产品接口，不代表现有二进制支持：

| 用户动作 | 产品行为 |
|---|---|
| init / design | 导入并固化文档，生成完整方案，组织独立设计审查 |
| plan | 基于批准方案创建全部切片与覆盖检查，等待或执行授权的计划批准 |
| approve / change | 审批精确候选或发起受控修订，不直接改执行状态 |
| run / resume | 由服务调度到完成或停止条件；不要求用户逐个派工 |
| status / explain | 只读对账并解释阶段、阻断原因与下一动作 |
| pause / cancel | 停止新调度、撤销 Worker 发布资格并处理在途动作 |
| bug report | 记录、去重和分诊；仅符合范围与预算的修复进入当前计划 |

首版采用单服务、单 GitHub 适配器、单 Agent Runtime、明确沙箱与凭据发布器；不预设旧包名、旧 CLI 格式、旧配置或旧 skill 安装机制。语言、数据编码和内部目录在实现切片契约中按这些边界设计，不为兼容已有代码增加组件。

| 实施里程碑 | 交付切片 | 阶段验收 |
|---|---|---|
| M1 协议与启动门 | GitHub 记录/身份协议；设计与独立审查；Planner/覆盖检查；批准与冻结 | 给定文档产生完整可审查方案和有限计划；未批准/漂移/缺项不能执行 |
| M2 单切片安全闭环 | Runtime/沙箱；可信发布器；一个 Developer 和独立验收；严格合并门；双端清理 | 一个真实 Issue 自动完成 PR→失败整改→验收→合并→清理 |
| M3 质量与恢复闭环 | Bug/Change；run 预算；幂等对账；旧 Worker 围栏；断点恢复 | 故障注入不重复交付、不洗预算、不接受失效证据；缺陷真实闭环 |
| M4 有界项目交付 | DAG 调度/有限并行；串行合并；固定候选整体验收；停止结论 | 完成冻结的多切片项目后停止，报告交付和全部收尾事实 |

这里只定义产品实施范围，不是一份活动执行账本；正式开发前仍须按本设计生成 GitHub Milestones/Issues 并批准冻结。未经明确授权，本次设计不会创建远端任务、推送或合并。

## 11. 系统级验收场景

| ID | 必须证明的行为 |
|---|---|
| E2E-01 | 只有产品文档的仓库先形成设计和有限计划；批准前无产品实现提交 |
| E2E-02 | 缺需求覆盖、循环依赖、缺验收环境或重大待决项时不能冻结并执行 |
| E2E-03 | 修改已批准契约、删除/移动成员或依赖，立即使冻结校验失败 |
| E2E-04 | 同一 Issue 仅一个活动开发候选；开发和验收为独立实例/身份；待测代码无法拿到发布凭据 |
| E2E-05 | 故意实现错误产生真实失败与有限整改；改 AC、换 PR、换 Issue 均不能绕过失败和预算 |
| E2E-06 | PR head/base 或可信策略变化时旧 PASS 不能合并；无保护能力不能启用自动合并 |
| E2E-07 | 创建/发布/合并/删除步骤中断后从 GitHub 对账；超时不盲目重复创建，不重复合并 |
| E2E-08 | Controller 重启及旧 Worker 迟到时，只接受当前分配；额度不因本地清空而恢复 |
| E2E-09 | 原生自动关闭 Issue/删远程分支后不重复操作；设置关闭或规则阻止时准确补偿/阻塞；本地额外提交/未保存工作不丢失，部分失败可恢复 |
| E2E-10 | 原 PR 缺陷与合并后缺陷分别进入正确主记录；未通过回归不能关闭交付 gate |
| E2E-11 | 代码修复合并但尚未上线/环境复验失败时，Bug 不被误报 resolved；继续修复不用旧分支 |
| E2E-12 | 全部切片单测通过但集成失败时交付仍失败；新构建不能复用旧环境验收 |
| E2E-13 | 删除本地缓存后仅凭 GitHub 与受管宿主即可恢复；缺失远端证据则明确阻塞 |
| E2E-14 | 完成、停止、预算耗尽和待决状态清楚可区分；达到目标后不再新增需求 |
| E2E-15 | S1 主 Bug 阻断最终交付但不循环阻断合格的修复 PR/授权验证部署；合并关闭修复 Issue，目标复验后才关闭主 Bug |

## 12. GitHub 能力边界与复用原则

原则：GitHub 已有的对象、关系和自动动作直接使用；Projectctl 只补充设计/规划/Agent 执行/证据语义/对账及本地收尾，不重造一套平台。

| 能力 | GitHub 原生边界 | Projectctl 负责 |
|---|---|---|
| 合并后删远程分支 | 仓库级自动删除 head 分支；管理员可配置，保护规则可能阻止 | 预检配置、合并前封存、核查结果，必要时安全补偿 |
| 合并后关 Issue | 关联 PR 合入默认分支可自动关闭；自动关闭设置可被禁用 | 正确建立唯一关闭关联，查真实 closed，必要时补关 |
| 本地分支/worktree | 不由远端仓库设置管理 | 停止 Worker、保全资料、解除占用、精确删除/归档 |
| Issue 依赖和 Milestone | 原生存储依赖、分组 | 规划覆盖、DAG 与冻结校验，不复制关系字段 |
| Reviews / Checks / 保护规则 | 平台执行配置的合并限制 | 独立 Agent、可信签发、检查内容、正确的版本绑定 |
| 原生 auto-merge / merge queue | 有可用性/权限/套餐限制，满足原生门槛后触发合并 | 探测能力，不绕过自定义语义 Gate 或变更屏障 |
| Agent 与目标验收 | 不自动理解产品需求、完成设计或判断业务正确性 | 冻结设计、自主切片、隔离执行、Bug/交付闭环 |

关键官方依据：

- [自动删除 head 分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches)：只解决远程收尾，规则仍可阻止删除。
- [PR 与 Issue 关联](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)：`Closes #N` 面向默认分支；PR 目标不是默认分支时，正文关闭关键字不生效。
- [自动关闭 Issue 设置](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-auto-closing-issues)：默认开启但可禁用，不能仅假设。
- [Issue dependencies](https://docs.github.com/en/rest/issues/issue-dependencies)、[Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)：复用原生依赖和可信来源检查。
- [Merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)：sha 约束 head，不是 base 条件写入；[Merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)有组织与套餐边界，不能假定个人仓库支持。

初始化必须探测目标仓库权限、设置与套餐；未知不能当作已支持。本文不表示已经修改了任何仓库设置，也不表示自动流水线已实现。
