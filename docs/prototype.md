# 当前源码边界

本文只说明设计基线建立时仓库中已经提交的源码，避免把目标设计误认为已实现能力。全新产品规范统一由[流水线设计](pipeline-design.md)定义；现有代码不约束新架构。

## 已提交原型

当前已提交源码为 1.0 本地事件账本 CLI。它能够注册来源、保存任务契约、记录领取与验证、重建本地状态，并显式地把任务投影到 GitHub Issue。它不是 GitHub 唯一事实源的自动流水线，也没有目标设计中的 Controller、Planner、隔离 Agent Runtime、可信发布器或自动合并闭环。

该原型保留为历史实现参考。新产品不承诺兼容它的命令、配置、事件格式、安装目录或迁移路径；也不能用它的本地状态证明新版任务已经批准、验收或完成。

设计 Issue #1 与对应 PR 只提交产品设计和导航文档，不夹带运行时重写。工作区里尚未进入该 PR 的实验代码不属于设计基线，也不得被文档描述为当前可用功能。

## 构建与验证现有源码

从仓库根目录执行：

```bash
go build -o dist/projectctl ./cmd/projectctl
./dist/projectctl --help
go test ./...
go vet ./...
```

这些命令仅验证当前 1.0 原型。构建成功不表示全新流水线的任何实施里程碑已经完成。

原型的历史命令和格式仍由其随仓库提交的 skill 与 references 说明。阅读它们时应以当前二进制 `--help` 为准，不得从历史接口反推新架构。

## 新实现的起点

设计基线合并并记录精确提交后，Planner 才能按主规范建立 M1 的完整执行 Issues。首个建议切片是 GitHub 冻结依据只读验证器：从远端事实校验基线、批准、计划成员、契约引用和原生关系，输出可解释的通过或阻断报告；不读取旧账本作为权威，也不在同一切片实现 Agent 调度或合并。

目标接口、实施顺序与验收场景见[主规范第 10–11 节](pipeline-design.md#10-产品接口与实现切片)。
