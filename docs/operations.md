# 安装、恢复与故障处理

## 数据生命周期

安装前可用 `projectctl install --dry-run` 检查目标路径。可执行文件位于目标项目 `.project-control/bin/projectctl`（Windows 为 `projectctl.exe`）；内嵌 skill 按所选 Agent 安装。项目数据和可执行文件应区别对待：升级或默认卸载不应使项目遗失已记录的记忆。

安装器不自动改写项目指令文件、Git 配置或 CI。需要将项目数据纳入版本管理或设置 `.gitignore` 时，先按实际内容判断：规范、任务与必要账本适合版本化，测试日志可能含敏感数据或体积较大。不要无差别上传所有运行日志。

升级、卸载或彻底清除前，先停止正在使用这个项目账本的 Worker 和测试进程。跨平台共享时，为原始规范统一 Git 换行策略；原文哈希按字节校验，自动 LF/CRLF 转换也会被识别为变化，不能把此类变化静默当作已批准。

## 恢复次序

1. 保留当前目录及错误输出，运行 `doctor`。
2. 若只有投影缺失，运行 `rebuild`，再运行 `status`。
3. 若事件或快照内容不匹配，恢复可信备份，或记录可解释的迁移；不要手工删除异常事件来“修好”链条。
4. 检查进行中的租约、代码工作区和远端 PR，避免丢失未提交工作或重复执行外部写入。多 worktree 模式恢复唯一的 `--root`，并逐次调用指定对应 `--worktree`；不要复制账本到新的分支后继续运行。
5. 重新生成当前任务 context，核对规范版本、代码 SHA 和所有证据。

恢复成功应表示已确认的事实重新可读，而不是所有任务都变成 Ready。

## 常见情况

| 情况 | 处理 |
|---|---|
| 来源文件变化 | 审查变更、重新批准，重建受影响上下文和验证 |
| 租约过期 | 核对旧 worker 与代码现场，按 CLI 状态允许的路径恢复或重试 |
| 验证失败 | 保留日志，判断代码、环境还是规范问题，受预算约束地修复 |
| 没有独立 Reviewer | 生成评审包并交接；开发者不自行最终验收 |
| GitHub 超时 | 查询远端结果与同步计划，再决定是否重试 |
| task 不可 Ready | 处理来源批准、依赖、decision 或 blocker；不强行改投影 |
| 上下文超出预算 | 拆任务或扩大预算，保留关键原文，不静默截断约束 |
| worktree 不属于相同 Git common directory | 使用同一 Git 仓库的工作区；不要用普通 clone 或复制账本规避检查 |

`doctor` / `audit` 的账本检查不等于产品设计符合性审计。后者还需要逐项核查需求、代码行为与测试证据。

## 备份与卸载

备份应覆盖原始事件、来源快照、上下文及必要验收证据，并与对应代码版本保持可追溯关系。哈希不是备份；引用某条 PR 链接也不能替代已过期的测试产物。

默认卸载移除安装器管理的可执行文件和 skill，保留数据及安装收据，后续可通过 `projectctl install` 重新安装：

```bash
projectctl uninstall --project /absolute/project
```

彻底清理时必须给外部 ZIP 备份路径：

```bash
projectctl uninstall --project /absolute/project --purge --backup /external/backups/project-control.zip
```

先检查备份成功，再验证压缩包可读取。卸载不会删除或撤销之前创建的 Issue、PR、评论、提交或远端保护设置。
